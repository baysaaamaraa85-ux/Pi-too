# ADR-017. VPS-ийн оронд Railway (PaaS) дээр байршуулах

> **Энэ файлын тухай.** `docs/02-system-design.md` нь зөвхөн унших (read-only) шинж чанартай тул ADR-ийг түүнд шууд нэмээгүй. Design-д оруулахдаа доорх гурван засварыг хийнэ (дарааллаар):
>
> 1. 9.1 хүснэгтэд мөр нэмэх: `| 017 | VPS-ийн оронд Railway (PaaS) дээр байршуулах | Байршуулалт | Батлагдсан | ХЗ-03, ФБШ-14, 16, 21, 30 |`
> 2. 9.1-ийн доорх өгүүлбэрт: "ADR-017 нь 2026.11.18-ны байршуулалтын шийдвэр бөгөөд 7-р бүлгийн VPS-ийн хэсгийг орлуулсан."
> 3. 7-р бүлгийн эхэнд тэмдэглэл: "2026.11.18-ны шинэчлэл (ADR-017): анхны нэг VPS дээрх Docker Compose төлөвлөгөөг Railway орлуулсан. Таван контейнерийн бүтэц хэвээр. Хөгжүүлэлтийн орчин Docker Compose хэвээр."
>
> Дараа нь доорх ADR-ийн хэсгийг 9.2 (ADR-005-ын дараа) руу хуулна.

**Төлөв:** Батлагдсан, 2026.11.18. 7-р бүлгийн "нэг VPS" гэсэн хэсгийг орлуулна. **Холбоотой:** ХЗ-03, ФБШ-14, 16, 21, 30.

**Нөхцөл.** Анхны төлөвлөгөө нэг VPS дээр Docker Compose-оор таван контейнер ажиллуулах байв (7-р бүлэг). Системийг багш нарт ашиглуулахаар байршуулах үед нэг хөгжүүлэгч сервер (үйлдлийн системийн шинэчлэл, галт хана, TLS гэрчилгээний сунгалт, нөөцлөлтийн cron, хяналт)-ийг дангаараа хариуцах нь хөгжүүлэлтийн цагийг хасна. Вэбийг Vercel-д байршуулах санал гарсан боловч Vercel-ийн Hobby багц арилжааны хэрэглээг хориглодог тул бизнест Pro багц (сард $20) хэрэгтэй. Үүнээс гадна Vercel нь тасралтгүй ажиллах процесс (worker, 10 секунд тутмын outbox), серверийн диск (`/uploads`), өгөгдлийн сан өгдөггүй тул API, worker, өгөгдлийн санг тусдаа хостод байрлуулах шаардлага үлдэнэ.

**Хувилбарууд.** (1) Нэг VPS дээр Docker Compose (анхны төлөвлөгөө). (2) Вэбийг Vercel Pro, API ба worker-ыг өөр хост, өгөгдлийн санг тусдаа үйлчилгээнд. (3) Бүх контейнерийг нэг PaaS (Railway) дээр.

**Шийдвэр.** (3). Контейнерийн бүтэц хэвээр, ажиллуулах орчин өөрчлөгдсөн:

| Анхны (7-р бүлэг) | Railway дээр | Тайлбар |
| --- | --- | --- |
| proxy (Caddy) | `web` service, `deploy/docker/web.Dockerfile` | TLS-ийг Railway-ийн edge дуусгана, Caddy HTTP-ээр сонсоно. React-ийн build, `/api`, `/uploads`, `/health` дамжуулалт хэвээр |
| api | `api` service, `deploy/docker/api.Dockerfile` | Нийтийн домэйнгүй, зөвхөн дотоод сүлжээ. `/uploads` нь volume дээр |
| worker | `worker` service, api-тай ижил Dockerfile, `SERVICE_ROLE=worker` | "api-тай ижил image, өөр эхлүүлэх команд" хэвээр. Яг нэг replica |
| db | Railway Postgres service, volume автомат | Public Access идэвхгүй |
| backup | `backup` service, cron (UTC 20:00 = Улаанбаатар 04:00) | `pg_dump` ба S3, 30 хоног хадгална |

Migration нь `api`-ийн pre-deploy командаар (`npm run db:deploy`) шинэ хувилбар гарахаас өмнө ажиллана, амжилтгүй бол шинэ хувилбар гарахгүй. Энэ нь 7-р бүлгийн "migration-ийг эхлээд ажиллуулж, дараа нь api ба worker-ийг солино" гэсэн дүрэмтэй тэнцүү.

**Зардал (ойролцоо, ачаалал багатай гэж таамагласан).** Railway-ийн Pro багц сард $20 (багцад $20 хэрэглээ багтсан), нөөцийн үнэ: санах ой $10/GB/сар, CPU $20/vCPU/сар, volume $0.15/GB/сар, гарах трафик $0.05/GB. Таамаглал (400-500 сурагч, 8 салбар): api 0.5 GB, worker 0.3 GB, Postgres 0.5 GB, Caddy 0.05 GB буюу нийт ~1.35 GB (~$13.5), дундаж CPU ~0.25 vCPU (~$5), volume 2 GB (~$0.3), трафик ~10 GB (~$0.5). Нийт ~$19-20 нь Pro-ийн багтсан $20-д ойролцоо багтах тул **сард ойролцоогоор $20-30**. Нөөцлөлтийн bucket тусдаа (бага). Эдгээр бол таамаглал: эхний сарын дараа Railway-ийн Usage хуудаснаас бодит хэрэглээгээр шинэчилнэ. Харьцуулалт: VPS (2 vCPU, 2-4 GB) нийлүүлэгчээс хамаарч сард ойролцоогоор $6-12 боловч сервер хариуцах ажил хөгжүүлэгч дээр үлдэнэ (үнийг нийлүүлэгчийн сайтаас шалгаагүй). Vercel Pro ($20) нь зөвхөн вэбийн хэсэг тул API, өгөгдлийн сан, worker-ийн зардал дээр нэмэгдэнэ.

**Үр дагавар.**

Давуу:
- Сервер, үйлдлийн систем, галт хана, TLS гэрчилгээг хөгжүүлэгч хариуцахгүй. GitHub-д push хийхэд автоматаар build, deploy хийгдэнэ.
- Api, өгөгдлийн сан нь нийтийн интернэтэд нээлттэй биш, зөвхөн Railway-ийн дотоод сүлжээнд (ФБШ-21, 7-р бүлгийн холболтын хүснэгтийн дүрэм хэвээр).
- Dockerfile, Caddyfile нь Railway-аас хамаарахгүй. Хэрэв хожим өөр орчин (VPS) руу буцах шаардлагатай бол ижил image-ийг ажиллуулна, vendor lock-in бага.
- Хэрэглээгээр төлнө: ачаалал бага үед зардал бага.

Сул:
- Зардал хэрэглээгээр өсдөг, урьдчилан тогтмол биш. VPS-ийн тогтмол үнэтэй харьцуулахад таамаглахад хэцүү.
- Нэг нийлүүлэгчээс хамааралтай: Railway-ийн тасалдал бүх системд нөлөөлнө. ФБШ-14 (сарын 99%)-ийг Railway-ийн хүртээмжээр биш, гадаад мониторингоор хэмжинэ.
- Railway-ийн "Config as Code" (`railway.json`) deprecated (2026-12-01-ээс уншигдахаа болино), шинэ "Infrastructure as Code"-д Dockerfile-ийн замын заалт баримтжаагүй тул service-ийн тохиргооны нэг хэсэг (pre-deploy, healthcheck, cron, volume) UI дээр гараар хийгдэнэ. Тэдгээрийг `DEPLOY.md`-д бичсэн.
- Серверийн бүс Монголоос алс байж болох тул хоцролт нэмэгдэж болзошгүй (ФБШ-04, LCP 2.5 секунд). Нийтийн хуудас PWA-ийн кэштэй тул нөлөө хязгаарлагдмал, гэхдээ ачааллын тестээр шалгана.
- Postgres-ийн хувилбар, өргөтгөл (`btree_gist`)-ийг Railway-ийн template тодорхойлно, баримт нь тодорхой тусгаагүй. 16 хувилбар баталгаагүй (`DEPLOY.md` 3.1).
- Volume нь нэг service-д холбогддог тул `/uploads`-ыг `api` өөрөө үйлчилнэ (Caddy шууд уншихгүй). Хэд хэдэн replica болгож өргөтгөх шаардлага гарвал зургийг объект хадгалалт руу шилжүүлнэ.

**Шаардлагатай зөрчил (хэрэглэгч шийдэх).** `01-requirements.md`-ийн ХЗ-03 ("Систем Docker-оор VPS дээр байршина") ба ФБШ-30 ("Docker Compose-оор нэг командаар шинэ серверт 30 минутын дотор суулгагдана") нь VPS гэж бичсэн тул энэ шийдэлтэй текстээрээ зөрчилдөнө. Docker-оор байршуулах нь хэвээр, `docker-compose.yml` хөгжүүлэлтэд хэвээр байгаа тул ФБШ-30-ыг "шинэ орчинд Dockerfile-аас 30 минутад" гэж тайлбарлаж болох ч, шаардлагын баримтыг энэ ADR-аар өөрчлөхгүй. Удирдагчтай зөвшилцөж ХЗ-03, ФБШ-30-ыг шинэчлэх эсэхийг шийднэ. Мөн ХЗ-03-ийн "сарын зардал төвийн баталсан хэмжээнээс хэтрэхгүй" гэсэн заалтын дээд хэмжээ (шаардлагын нээлттэй асуулт) тогтоогдоогүй, дээрх зардлыг төвд танилцуулах хэрэгтэй.

**Дагалдах өөрчлөлт.** Migration `20261021135641_constraints` нь `pitoo_app` нууц үгийг (`pitoo_app_dev`) болон өгөгдлийн сангийн нэрийг (`pitoo`) шууд бичсэн нь нийтийн сан дээр аюултай, мөн нэр өөр сан дээр унадаг байв. Нууц үгийг `APP_DATABASE_URL`-аас авдаг `prisma/bootstrap-app-role.ts` (migration-аас өмнө) руу, сангийн нэрийг `current_database()` руу шилжүүлсэн. Ингэснээр `ALTER ROLE` хийх шаардлагагүй (ФБШ-24, ФБШ-29). Хэрэглэгдсэн migration-ийг засах нь CLAUDE.md-ийн дүрмээс гажсан тул хэрэглэгчийн шууд зөвшөөрлөөр хийж, `docs/decisions-log.md` D-91-д бүртгэв. Мөн үйлдвэрийн (production) орчинд seed нь нийтэд мэдэгдэх нууц үгтэй жишээ багш нар үүсгэхгүй болгосон (D-92), proxy-ийн ард rate limit зөв ажиллахын тулд `TRUST_PROXY` тохиргоо нэмсэн (D-93).
